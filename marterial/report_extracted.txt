Section 3 — Reflection (4%)
Developing M-Hike across a native Android (Java) application and a React Native cross-platform prototype was a substantial exercise in applied mobile software engineering. The Android codebase was organised around the Model–View–Controller pattern, with a dedicated helper class, FirestoreHelper.java, decoupling user-interface logic from Cloud Firestore persistence in a manner consistent with the repository pattern described by Gamma et al. (1994). This separation made the Activities and Fragments considerably easier to test and to reason about individually.
One achievement I am satisfied with is the integration of Firebase Authentication with Cloud Firestore for real-time, bidirectional data synchronisation, and the creative extension built around the Mapbox Maps SDK v11. To keep the custom map marker crisp across the wide range of Android screen densities, I combined a base CircleAnnotation with a vector PointAnnotation icon into a single dual-layer pin, and I built a three-tier geocoding fallback chain — the Android system Geocoder, followed by OpenStreetMap Nominatim, followed by Komoot Photon — so that address resolution remains reliable even when one provider is rate-limited or unavailable.
The most significant technical challenge was a touch-handling conflict: placing an interactive Mapbox MapView inside a NestedScrollView caused the parent container to intercept vertical swipe gestures intended for the map. I resolved this by calling v.getParent().requestDisallowInterceptTouchEvent(true) on MotionEvent.ACTION_DOWN, giving the map exclusive control of panning gestures. Debugging this issue taught me to read touch-event propagation in Android far more carefully than before.
If I were to rebuild the application, I would migrate the Android architecture from MVC to Model–View–ViewModel, using Jetpack's StateFlow and LiveData to remove callback boilerplate and improve lifecycle safety, and I would add an offline map-tile cache through the Mapbox Offline Manager so the app remains genuinely useful to hikers in areas without reliable connectivity. Overall, the project strengthened my understanding of layered architecture, third-party SDK integration, and the trade-offs between native and cross-platform development.

Section 4 — Evaluation (10%)
Evaluating a mobile application requires a systematic analysis of usability, security, adaptability and deployment readiness rather than a subjective impression of the finished product. A well-implemented feature list is not, by itself, evidence of a well-engineered application: the same functionality can be delivered through an interface that is confusing, insecure, or unable to cope with the diversity of Android hardware in real use. The five subsections below therefore assess M-Hike against established human–computer interaction (HCI) criteria, mobile security standards, cross-device responsiveness, live-deployment requirements, and one additional technical consideration specific to the libraries used in this project, in each case using authoritative external references to justify the judgement reached rather than relying on unsupported opinion.
4.1 Human–Computer Interaction (HCI)
M-Hike follows Google's Material Design 3 guidelines throughout, using an 8dp spacing grid, elevated cards, colour-coded difficulty chips and consistent iconography to establish a predictable visual hierarchy across every screen (Google, 2024). Because the target users are hikers who may be reviewing or entering data outdoors, in bright sunlight or with limited attention available, the interface deliberately favours large touch targets, high-contrast text and a single, unambiguous primary action per screen (for example, 'Save Hike' or 'Confirm & Save') rather than dense menus of secondary options. 4.3 Ability to Run on a Range of Screen Sizes
Android devices span an unusually wide range of screen sizes and pixel densities, and the official Android documentation recommends density-independent units and flexible layout containers to accommodate this variation (Google, 2024a). M-Hike was built accordingly:
Density-independent units — all dimensions are defined in dp and all typography in sp, so layouts respect the user's OS-level font-scaling accessibility settings without breaking, and text does not become illegible on high-density or low-density panels.
Flexible layout managers — ConstraintLayout and CoordinatorLayout reposition and resize components relative to the available width and height, avoiding clipping or overlap on both small (4.7-inch) budget phones and large (6.7-inch) flagship phones tested during development.
Vector graphics — icons and the custom map marker are XML vector drawables rather than fixed-resolution bitmaps, so they remain sharp on high-density (xxxhdpi) displays without inflating APK size or requiring multiple exported image sizes.
Scrollable containers — every data-entry and list screen is wrapped in a scrolling container, so content that does not fit a shorter screen remains reachable rather than being clipped off-screen.
Proposed improvement: the application has not yet been optimised for tablets or foldable devices. Introducing a smallest-width resource qualifier (e.g. layout-sw600dp) to deliver a two-pane master–detail layout — a hike list on one side and the selected hike's details, map and observations on the other — as recommended in Google's large-screen guidance (Google, 2024b), would make far better use of the additional horizontal space than simply stretching the existing phone layout across a bigger canvas. Manual testing on only two physical devices during development is also a limitation: before deployment the layout should be verified on the Android Emulator's full range of reference devices, from small 4-inch phones to 12-inch tablets, to catch any remaining clipping or overlap issues.
4.4 Changes Required for Live Deployment
Moving M-Hike from an academic prototype to a production release on the Google Play Store would require several changes beyond the current implementation:
API key protection — the Mapbox token and Firebase configuration must be obfuscated/restricted (API key rotation, Android package-name and SHA-1 restrictions in the Google Cloud console) to prevent quota theft.
Build hardening — enabling R8/ProGuard minification and resource shrinking in the release build variant to reduce APK size and deter reverse engineering.
Monitoring — integrating Firebase Crashlytics and Google Analytics for Firebase to capture unhandled exceptions and usage metrics once real users are involved.
Formal security review — completing a full OWASP MASVS checklist and, ideally, a third-party penetration test before handling live user location data at scale.
4.5 Other: Native Library Forward-Compatibility
Additional technical evaluation — 16 KB page-size compatibility: recent Android releases (Android 15/16) enforce 16 KB memory-page alignment for native shared libraries; applications built against older native (.so) binaries can crash immediately on launch on this newer hardware, even though the same build runs correctly on older devices. M-Hike's Mapbox dependency was compiled against the NDK r27 binaries, which are already aligned to this requirement, so the application is forward-compatible with next-generation Android devices without further changes (Google, 2024c). This is a useful example of a small, easily overlooked dependency-version decision having a disproportionate effect on long-term stability, and it is exactly the kind of regression that conventional functional testing on existing devices would not surface without deliberately targeting the newest OS images in the test matrix. It also illustrates a broader evaluation point: technical debt in a student project is not only about features left unbuilt, but about dependencies whose assumptions quietly go out of date as the underlying platform evolves, which is why version-pinning decisions were documented rather than left implicit in the build configuration.

Listing 5.1 — AddHikeActivity.java (touch-intercept handling & dual-layer marker pin)
Overview: resolves the NestedScrollView/Mapbox touch conflict described in Section 3, and renders the custom two-layer red marker used for GPS confirmation.
// Touch listener: stop the parent NestedScrollView intercepting swipe
// gestures meant for the embedded Mapbox map (see Section 3, Reflection).
previewMap.setOnTouchListener((v, event) -> {
    switch (event.getAction()) {
        case MotionEvent.ACTION_DOWN:
        case MotionEvent.ACTION_MOVE:
            v.getParent().requestDisallowInterceptTouchEvent(true);
            break;
        case MotionEvent.ACTION_UP:
        case MotionEvent.ACTION_CANCEL:
            v.getParent().requestDisallowInterceptTouchEvent(false);
            break;
    }
    return false;
});
// Dual-layer red marker pin: a base circle annotation plus a vector
// point-annotation icon, rendered together for a crisp, on-brand pin.
private void updatePreviewMarker() {
    try {
        double lat = Double.parseDouble(editLat.getText().toString());
        double lng = Double.parseDouble(editLng.getText().toString());
        Point p = Point.fromLngLat(lng, lat);
        previewMap.getMapboxMap().setCamera(
            new CameraOptions.Builder().center(p).zoom(14.0).build());
        AnnotationPlugin annotationApi = (AnnotationPlugin)
            previewMap.getPlugin(Plugin.MAPBOX_ANNOTATION_PLUGIN_ID);
        // Layer 1: vibrant red target circle
        circleAnnotationManager.deleteAll();
        circleAnnotationManager.create(new CircleAnnotationOptions()
            .withPoint(p).withCircleRadius(12.0)
            .withCircleColor("#FF1744").withCircleStrokeWidth(3.0)
            .withCircleStrokeColor("#FFFFFF"));
        // Layer 2: vector red pin icon
        pointAnnotationManager.deleteAll();
        Bitmap bitmap = getBitmapFromDrawableRes(R.drawable.ic_red_marker);
        pointAnnotationManager.create(new PointAnnotationOptions()
            .withPoint(p).withIconImage(bitmap)
            .withIconSize(1.2).withIconAnchor(IconAnchor.BOTTOM));
    } catch (Exception ignored) { }
}
Listing 5.2 — FirestoreHelper.java (data persistence wrapper)
Overview: encapsulates Cloud Firestore CRUD operations so that Activities and Fragments never talk to Firestore directly, keeping the UI layer testable.
public class FirestoreHelper {
    private FirebaseFirestore db = FirebaseFirestore.getInstance();
    public void insertHike(Hike hike, DataStatus status) {
        db.collection("hikes")
          .add(hike)
          .addOnSuccessListener(documentReference -> {
              hike.setFirebaseId(documentReference.getId());
              db.collection("hikes")
                .document(documentReference.getId())
                .set(hike);
              status.dataIsInserted();
          })
          .addOnFailureListener(e ->
              Log.e("Firestore", "Error adding hike", e));
    }
}

Listing 5.3 — HikeContext.js (React Native persistence)
Overview: uses the React Context API together with AsyncStorage to persist and rehydrate hike records on the cross-platform build, implementing Functionality F.
import React, { createContext, useState, useContext, useEffect }
  from 'react';
import AsyncStorage from '@react-native-async-storage/async-storage';
const HikeContext = createContext();
export const HikeProvider = ({ children }) => {
  const [hikes, setHikes] = useState([]);
  useEffect(() => { loadHikes(); }, []);
  const loadHikes = async () => {
    try {
      const stored = await AsyncStorage.getItem('@hikes');
      if (stored) setHikes(JSON.parse(stored));
    } catch (e) {
      console.error('Failed to load hikes from storage', e);
    }
  };
  const addHike = async (newHike) => {
    const updated = [newHike, ...hikes];
    setHikes(updated);
    await AsyncStorage.setItem('@hikes', JSON.stringify(updated));
  };
  return (
    <HikeContext.Provider value={{ hikes, addHike }}>
      {children}
    </HikeContext.Provider>
  );
};
export const useHikes = () => useContext(HikeContext);
